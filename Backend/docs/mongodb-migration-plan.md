# Controlled MySQL → MongoDB cutover plan

The SQL migrations and data must remain untouched. MongoDB uses an independent `mongo_migrations` graph (including contrib auth/admin/contenttypes and JWT blacklist); old relational migrations cannot be replayed with unsupported AutoFields. Legacy connection configuration will remain in `rideflow/legacy_mysql.py` for read-only export/rollback. Never point the MongoDB migration graph at MySQL.

1. Inventory and back up MySQL plus private media; record app versions, row counts, checksums, users/groups/permissions, active rides/assignments, quotes, document paths and audit/event sequences. Restore the backup into an isolated source first.
2. Rehearse export/import against that restored source and a new isolated replica-set database. Export must be non-destructive. Stop application/worker writes for the final consistent snapshot; do not rely on a cross-database transaction.
3. Preserve existing UUID and natural slug keys. Map every old integer PK deterministically to an ObjectId, recording model + old PK → new PK. Rewrite every FK/M2M reference with the same map. Hash passwords remain unchanged. Preserve identities/groups/admin flags; align permissions by app/model/codename because post-migrate seeds target permissions with fresh keys.
4. Preserve Decimal amounts, UTC millisecond timestamps, payment preferences, quote snapshots and media storage names. Normalize ObjectIds in JSON snapshots to strings and rebuild the exact matching pricing version/snapshot. Convert driver coordinates to GeoJSON `[longitude, latitude]` and build the 2dsphere index. Snapshot fingerprints must be checked against the migrated quote/booking fields before allowing retry reuse.
5. Reconcile counts and canonical content checksums, uniqueness, every FK/M2M reference, permission assignments, one active assignment per ride/driver/passenger and agreed fares. Validate actual account login, admin permissions, document download, quote/booking/offer/trip history and replica-set concurrency. Refuse cutover on any mismatch. Import may revoke existing sessions/JWT refresh tokens intentionally: integer user IDs in existing tokens cannot silently become ObjectIds. Require fresh OTP/admin login.
6. Run a final frozen export/import and reconciliation; switch app/worker environment to MongoDB only after sign-off on the rehearsal report. Keep the source read-only with backups for rollback. No source records or SQL migration files are deleted. Never run both databases as independent live writers.
7. For rollback before new MongoDB writes, restore the old application revision/settings and source database. After new writes, stop traffic and reconcile/export those writes before rollback; switching the URI alone would lose data.

Implementation/testing report will record which source/rehearsal data was actually verified. No claim of production data migration is made without an actual source snapshot and reconciliation. The transfer command defaults to a planning/dry-run workflow and requires an explicit apply flag for the isolated target.

Official references: [configuration/contrib migrations](https://django-mongodb-backend.readthedocs.io/en/5.2.x/intro/configure/), [feature compatibility](https://www.mongodb.com/docs/languages/python/django-mongodb/v5.2/limitations-upcoming/), [official transaction API](https://www.mongodb.com/docs/languages/python/django-mongodb/v5.2/interact-data/transactions/).
